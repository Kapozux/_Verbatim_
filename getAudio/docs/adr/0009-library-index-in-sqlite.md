# 0009 转写列表和搜索走 SQLite 索引，文件仍是唯一的原始数据

日期：2026-10-03

## 背景

资料库、转写页「最近转写」、资料库搜索都是现读 `results/<tid>/` 下的文件：列一次转写读 3410 份 meta.json
（0.1 秒），搜正文时把 140 MB 的 transcript.json 逐个读进来找（0.6–1.2 秒）。最近转写只要 12 条，也得先读全部
再排序。用户：「你就不能缓存吗」「如果 SQLite 已经有时间复杂度快的算法就直接用」。

考虑过的做法：
- **进程内存缓存**：每次还得 stat 3410 个文件才知道有没有变；搜正文仍要逐句扫 4900 万字；重启就没了。
- **自己写倒排索引**：中文没有空格，要自己切 n-gram、自己存、自己管并发——SQLite 的 FTS5 trigram 就是这个。
- **把 meta / 正文直接改存进 SQLite，不要文件**：所有读写转写的地方（几十处、外部脚本、MCP、备份）都得改，
  备份和手工查看也变难。

真实数据试建（3410 条、正文 4900 万字）：取最新 12 条 0.07 ms；FTS5 trigram 搜「量子计算」1.6 ms、「nvidia」3 ms；
两个字（「利率」）trigram 用不上，在库里整表扫 70 ms。第一次建 8–13 秒。detail=full 365 MB，detail=none 192 MB，
LIKE 搜出来的一样。

## 决定

1. **文件仍是唯一的原始数据，`library.db` 只是索引**（数据目录下，跟 tasks.db 放一起）。删了它下次启动自动重建；
   备份只同步 `results/`，不带它。
2. **一张 `docs` 表**（id、date、meta 原文、搜索要看的 meta 字段小写拼成的 `hay`、两个文件的修改时间），date 上建索引；
   **一张 FTS5 表 `body`**（trigram，detail=none），存每句正文（句与句之间用 \x1e 隔开，命中不会跨句）和对应时间戳。
3. **搜索结果跟原来逐个读文件一字不差**：meta 字段命中（`instr`，跟原来 `in` 一样区分大小写前先都转小写）的片段为空；
   否则正文 `LIKE` 找候选，再在 Python 里按原来的规则找第一句命中的、切「前 20 字 + 命中 + 后 40 字」。
   `tests/test_library.py` 把原来的写法原样搬进去逐条对照；上线前在真实数据上 16 个查询逐条对照过。
4. **保持一致**：写 `results/<tid>/` 的地方写完调 `library.changed(tid)`（现在 5 处写、2 处删）；每次读之前列一遍
   `results/`（约 1 ms），新出现、消失的目录当场补上；每 60 秒在后台按修改时间对一次账，兜住脚本、手工直接改文件。
5. **正文还没进索引的**（第一次建的那十来秒、刚出现还没建的）搜索时退回直接读那几个文件；**SQLite 出任何错**都退回
   原来逐个读文件——索引坏了只是变慢，不会少结果。

## 后果

- 最近转写 122 ms → 3 ms；搜索 600 ms → 7–150 ms（命中上千条的，时间主要花在把结果传回去）。
- 多占 190 MB 左右磁盘（正文的 1.4 倍左右），随转写增长。
- 新写 `results/<tid>/meta.json` 或 `transcript.json` 的代码必须调 `library.changed(tid)`；漏了也不会错，只是最多晚 60 秒
  才在列表 / 搜索里变（`getAudio/CLAUDE.md` 工作约定里写了）。重构分支的 `transcripts.py` 是这些文件唯一的写入者，
  合并时把 `changed` 挪进它里面，别处就不用再记。
- 搜索里非 ASCII 字母的大小写（如 É / é）只有在 meta 字段里不区分；正文 LIKE 只折叠 ASCII 大小写——中英文语料基本碰不到。
